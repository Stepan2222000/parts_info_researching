# Авто-курация очереди

## Проблема

В очереди ~1550 `done`-ранов без публикации. Гонять LLM-куратора по всем батчам дорого и шумно, руками — неподъёмно. Замер по живой очереди (2026-07-26): у ~90% ранов с матчем в prod-`smart` ровно один match по артикулам — решение детерминированное, модель не нужна. Но 39% очереди — «майские» раны (до миграции 004) вообще без `vehicle_classes`, а 23% — пересекаются confirmed-номерами с соседями (группы).

## Принцип

Слои от дешёвого к дорогому, каждый обрабатывает только остаток предыдущего. Никакой слой не выдумывает данные и не снимает замки (`is_draft=false` / `is_unverified=false`).

0. **Бэкфилл классов** (дешёвый LLM) — разово чинит майские раны.
1. **Автопроход** (без LLM) — публикует однозначное; воронка похожести помечает возможные дубли.
2. **Hard list** — остаток с типизированной причиной. Фильтр, не статус.
3. **LLM-куратор с web-поиском** — батчами разбирает hard list и дедуп-очередь, публикует сам.

Человеку — только `frozen_or_final` и то, в чём куратор сам расписался «не уверен».

## Шаг 0 — бэкфилл классов (`cli.backfill_classes`)

607 done-ранов от 30–31 мая сделаны по контракту до миграции 004: `vehicle_classes` пуст, но имя, бренд, описание, модели и старый `product_type` есть — классы восстановимы без web. Пачки по 20 → judge-модель (strict-схема) → классы в `draft_parts.vehicle_classes` + след в `draft_parts.classes_backfill` `{model, at, confident}`. Не уверена модель — ран остаётся без классов и уходит куратору как `no_classes`. Прогон на 15 живых ранах: 15/15 корректно (Skandic→snowmobile, Sea-Doo→jetski, Mercedes→auto, мультикласс BRP), ~360 токенов/ран.

Полный ресёрч этих ранов не перезапускаем — дорого; классы — единственный блокер автопрохода.

## Слой 1 — автопроход (`cli.curation_sweep`)

Существующие гейты «зелёного коридора» (`auto_publish.py`) прогоняются пакетно по всем неопубликованным done-ранам (последний ран задачи). Публикуем без человека, когда всё сразу:

- есть `name`, непустые `vehicle_classes`, есть confirmed-номера;
- ран — «группа из одного»: confirmed не пересекаются с другими неопубликованными done/nhr-ранами;
- по confirmed в `smart` ровно 0 записей (INSERT) либо ровно 1 (UPDATE);
- найденная запись `is_draft=true`; для набора состав не заморожен;
- нет конфликта с irrelevant-номерами; бренды в `smart.brands`; title влезает.

**Группы слой 1 не сливает никогда.** Замер показал: формально «однородная» группа детерминированно не разбирается — в семейство supersession водяной помпы затесался Carrier Assembly, к винтам 14x19 RH — винт другой серии; это ровно кейс 806552A1 (supersession ≠ эквивалент). Все группы уходят слою 3.

Исход каждого рана — в `task_runs.auto_publish_outcome` (published / skipped+reason / error), идемпотентно, сериализовано advisory-lock'ом. `--dry-run` гоняет только гейты в откатываемой транзакции. Ожидание по замеру: ~550 публикаций сразу + большинство майских после шага 0 → суммарно ~⅔ очереди.

Одновременно с разбором завала включаем `RESEARCH_AUTO_PUBLISH` на проде — иначе очередь копится заново.

## Воронка похожести — анти-дубли (`similar.py`)

Замер (1548 ранов × 1098 записей): ни один порог текстовой похожести не работает сам — у пар с общим артикулом (заведомо одна деталь) медианная похожесть 0.41, а топ рейтинга — родовые «Сальник ↔ Сальник». Жёсткие вето (класс, размер) убивают настоящие дубли. Поэтому три ступени:

1. **Шорт-лист** (детерминированный, мгновенный): мягкий скор — имя RU/EN (токены+fuzzy), пересечение моделей, описание, бонусы за бренд/класс; без вето. Топ-80 ловит настоящий дубль в 98% случаев (топ-40 — 96.7%). Из имён/описаний извлекаются спеки (30x60x37, шаг 14x19, M8x1.25) — как разметка для судьи.
2. **LLM-судья** (`LLM_MODEL_JUDGE`, флаг `RESEARCH_DEDUP_JUDGE`, по умолчанию on): после каждого авто-INSERT смотрит карточки шорт-листа и решает same / likely_same / unsure / different. Проверено на стресс-кейсах: винты различает по шагу и стороне вращения, родовые сальники честно `unsure`, настоящие дубли с разными именами находит. ~3 тыс. токенов на ран. Вердикты same/likely_same → `dedup_candidates` (+ сводка в `outcome.similar`). Судья работает ПОСЛЕ коммита публикации и ничего не блокирует; флаг можно выключить в любой момент без побочных эффектов.
3. **Слияние — только куратор с пруфом** (см. слой 3). Автослияния по имени/описанию нет ни при каком пороге: ложная склейка дороже дубля.

Шорт-лист топ-5 также подмешивается куратору в `get_context` (`similar_by_name` на карточке).

**Жёсткая сцепка — только по артикулам.** Имя/модель/описание — всегда мягкий сигнал.

## Слой 2 — hard list

Не новый статус, а фильтр: done-раны с `auto_publish_outcome.decision='skipped'`. Причина типизируется из текста (`classify_skip_reason`):

| тип | смысл | кто разбирает |
|---|---|---|
| `group` | confirmed пересекаются с другими ранами | LLM-куратор |
| `ambiguous_smart_match` | номера бьют в 2+ smart-записи | LLM-куратор |
| `data_conflict` | номера существующей записи помечены раном irrelevant | LLM-куратор |
| `no_classes` | классов нет и после бэкфилла | LLM-куратор |
| `brand_missing`, `title_too_long`, `bad_article_format` | формальные блокеры | LLM-куратор |
| `incomplete_draft` | нет имени/confirmed-номеров | LLM-куратор |
| `frozen_or_final` | `is_draft=false` либо состав заморожен | **человек** |

UI: чип «Hard list» в дашборде (кликабельный фильтр), причина — на карточке. Замер: доминируют группы; `ambiguous`/`frozen`/`brand_missing` — единицы.

## Слой 3 — LLM-куратор (`cli.curate_hard_list`)

- Батчи ≤ `CURATOR_GET_CONTEXT_MAX_PARTS` (25) деталей ОДНОГО типа причины; группы (связные компоненты по confirmed) не рвутся.
- Обязан искать в сети (`web_search_exa` / `web_fetch_exa`) до решения, а не парковать сразу.
- **Публикует сам**, без подтверждения человеком (`save_to_smart`).
- Группы: один товар → одна запись через `also_run_ids`; разные → раздельно, мостиковый номер остаётся законному владельцу.
- Слияние **без общего артикула** — только с пруф-URL; пруф фиксируется в `dedup_candidates` (status='merged', proof_urls). Нет пруфа — раздельно.
- `frozen_or_final` не трогает; «не уверен» → `mark_needs_review` с причиной.
- Режим `--dedup`: разбирает открытые `dedup_candidates` (гипотезы судьи) — merged с пруфом / kept_separate.

## Порядок запуска

1. миграция 016 → 2. `backfill_classes` → 3. `curation_sweep` + включение `RESEARCH_AUTO_PUBLISH` → 4. `curate_hard_list` (типы по очереди, группы первыми) → 5. `curate_hard_list --dedup` → 6. человек добивает frozen и «не уверен».

Каждый шаг оставляет след (outcome, classes_backfill, dedup_candidates, curator-сессии) — всегда видно, кто, что и почему опубликовал.

## Чего не делаем

- Не пишем в записи с `is_draft=false` / `is_unverified=false` и не снимаем флаги автоматически.
- Не сливаем группы и похожие имена автоматикой — только LLM с пруфом из сети.
- Не дробим настоящий дубль на две smart-записи.
- Не заводим бренды в `smart.brands` сами.
- Не перезапускаем ресёрч майских ранов ради классов.
